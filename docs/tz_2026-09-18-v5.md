# v5 — встраиваемый анализатор для majento.ru

Задача на выходные 19–21.09.2026. Основано на переписке с заказчиком (Андрей) 18.09.

## Что это

Доработка **v1** до встраиваемого в чужой сайт скрипта с сопоставлением абзацев и
инфографикой. Одной фразой:

> Считаем векторы абзацев нашей страницы и указанных конкурентов, сопоставляем их
> между собой и показываем, что совпадает, чего у нас нет и что есть только у нас.

Заказчик одобрил именно это: **v1 + сопоставление с конкурентами + инфографика**.
GIST, краулер и LLM в объём не входят.

## Куда встраивается

Страница https://majento.ru/index.php?page=seo-analize как ещё один SEO-инструмент.
Факты о сайте (проверено в браузере 18.09):

- jQuery 1.11.1 + jQuery UI 1.11.1, fancybox, VK-виджеты, Яндекс.Метрика;
- инструменты — обычные PHP-формы: POST на `index.php` со скрытым полем `page`;
- вёрстка таблицами, **колонка контента ≈ 728px**, макет фиксированный, не адаптивный;
- глобальный `page.css` красит по тегам: `p`, `li`, `td` → 12px Arial; `h2`/`h3` →
  свой цвет и `letter-spacing`; `a:link/hover` → свои цвета;
- `progress { background-color: white !important }` — нативный `<progress>` использовать
  нельзя, их стиль перебьёт наш.

Доступа к сайту заказчик пока не даёт, отлаживаем локально.

## Алгоритм

Без усложнений. Один проход:

1. Скачиваем нашу страницу и до **4** страниц конкурентов (ссылки вводятся руками).
2. Извлекаем статью и режем на абзацы: `MIN_PARAGRAPH_LENGTH = 150`,
   `MAX_PARAGRAPH_LENGTH = 800` с разбивкой длинных по предложениям (как в v3 —
   `apps/v3/api/src/pages/services/content-extractor.service.ts`).
3. Считаем эмбеддинги запроса и всех абзацев.
4. Релевантность абзаца = косинус с запросом.
5. Матрица «наши абзацы × их абзацы», для каждого абзаца берём максимум по другой стороне.
6. Раскладываем по состояниям порогами.

Никаких GIST, отборов, весов, интегральных баллов и второго алгоритма.

### Ответ API

Релевантность — **не матрица**: запрос один, поэтому это одно число на абзац, свойство
самого абзаца. Матрица только одна — сопоставление абзацев. Векторы документа не считаем
(усреднение страницы в один вектор и даёт бесполезную матрицу, где всё около 0.92).

Матрица не сквозная по всем конкурентам, а **по одной на конкурента** — тогда
принадлежность столбца структурная и выпавшая страница это просто отсутствующий блок,
без пересчёта смещений.

```json
{
  "query": "как выбрать посудомоечную машину",
  "model": "multilingual-e5-small",
  "ours": {
    "url": "https://...",
    "paragraphs": [{ "heading": "Введение", "text": "...", "relevance": 0.42 }]
  },
  "competitors": [
    {
      "domain": "habr.com",
      "url": "https://...",
      "paragraphs": [{ "heading": null, "text": "...", "relevance": 0.51 }],
      "similarity": [
        [0.71, 0.63, 0.58],
        [0.44, 0.81, 0.52]
      ]
    }
  ]
}
```

`similarity` лежит внутри конкурента: строк столько, сколько абзацев у нас, столбцов —
сколько у него. `similarity[2][5]` — наш третий абзац против его шестого.

Что считает React при получении ответа, **один раз**:

- максимум по строке через все блоки — лучшее совпадение нашего абзаца и у кого найдено;
- максимум по столбцу — есть ли у нас пара для чужого абзаца.

Это единственный проход по ~14 тысячам чисел, и он **не зависит от порога**. Ползунок
дальше матрицу не трогает: он сравнивает с числом ~300 готовых максимумов, а его
дефолтная позиция — медиана по тому же массиву.

Ограничение шейпа: сходство конкурентов между собой в нём не выражается. Сейчас не нужно.

### Порог и шкалы

**Измерено на живых данных 19.09**, четыре разных корпуса:

| корпус                     | фон (медиана всех пар) | релевантность |
| -------------------------- | ---------------------- | ------------- |
| robots.txt, рус, 4 стр     | 0.834                  | 0.785 – 0.918 |
| iPhone, англ, 3 стр        | 0.821                  | 0.786 – 0.913 |
| Москва, рус, 2 стр         | 0.799                  | 0.778 – 0.839 |
| повторные роды, рус, 3 стр | 0.827                  | 0.845 – 0.902 |

**Абсолютной шкалы нет ни у одной оси**, но фон устойчив: 0.80–0.83 при любом языке,
жанре и теме. Это свойство модели, а не отдельного примера. Косинусов около 0.5 на
связных веб-текстах не бывает, поэтому пороги вида 0.35 или 0.65 не отсекают ничего.

Абсолютного порога «покрытия» нет. На вкладке рекомендаций используется только
относительный отбор: релевантность абзаца конкурента должна превышать среднюю
релевантность нашей статьи, а его максимальное сходство с нашим абзацем —
быть ниже одной из семи границ распределения этого прогона. Это не вердикт
«пробел», а сортируемый список кандидатов с обоими точными косинусами.

**Инструмент не судит о ценности текста.** Он показывает измеряемые свойства
фрагментов выбранных пользователем страниц; решение, нужен ли фрагмент статье,
принимает редактор.

**Что чистим механически, без суждений о смысле:**

- `MIN_PARAGRAPH_LENGTH = 150` вместо 40. Подобрано по данным: хлебная крошка занимает
  133 знака и умирает ровно на 150, при этом из статьи про повторные роды не теряется ни
  одного содержательного абзаца. Порог 200 уже режет живое. Цена принята сознательно —
  вместе с обвязом уходят и короткие смысловые абзацы;
- блоки `<pre>` с кодом и примерами конфигурации: это не абзацы статьи, поэтому не
  считаем им релевантность и не сопоставляем; inline-код внутри обычной фразы остаётся;
- **точные дубли** внутри страницы, чтобы одинаковый фрагмент не попадал в список
  несколько раз;
- фильтр по релевантности **не применяем** — см. выше.

Чего длина не берёт: подвал «Няня.ру — это виртуальный семейный центр…» занимает 455
знаков и переживёт любой порог.

## Модель

`Xenova/multilingual-e5-small` через **transformers.js** (onnxruntime) прямо в Node,
квантизация int8. Проверено: ONNX-сборки на HF есть, 384 измерения, **512 токенов**.

Предложенную заказчиком `paraphrase-multilingual-MiniLM-L12-v2` **не берём**: у неё
`max_seq_length = 128`, для русского это ~300–400 знаков, то есть абзацы до 800 знаков
молча обрезались бы. e5 требует префиксов `query:` / `passage:` — ставим их.

Модель греем на старте процесса. В образ кладём на этапе сборки, из рантайма с HF
не тянем.

## Интерфейс

Русский интерфейс, тексты абзацев — на языке источника. Светлая тема, ширина 728px,
одна прокрутка. После расчёта страница прокручивается к короткой шапке отчёта:
заголовок и кликабельный URL нашей страницы, поисковый запрос. Ниже две вкладки.

### Таб 1 — «Ваша статья» (по умолчанию)

- Число извлечённых абзацев и средняя косинусная релевантность их запросу.
- Список наших абзацев в исходном порядке статьи. Сортировки нет: она не даёт
  редакторского вывода и мешает читать статью как последовательный текст.
- Для каждого нашего абзаца: релевантность этого абзаца поисковому запросу,
  сходство с самым похожим фрагментом среди всех введённых конкурентных страниц,
  полный кликабельный URL источника и его заголовок. Раскрытие даёт оба полных
  текста для ручной проверки.
- Пояснение прямо говорит, как выбрана пара: перебираются все фрагменты всех
  введённых конкурентов, затем выбирается максимальный косинус. Это техническая
  лучшая пара, а не готовый вывод о совпадении смыслов.
- Первые восемь абзацев видны сразу; остальные открываются кнопкой.

### Таб 2 — «Абзацы конкурентов, рекомендованные для дополнения»

Кандидат — абзац конкурента, чья косинусная релевантность поисковому запросу
**выше средней релевантности абзацев нашей статьи**, а максимальное сходство
с любым нашим абзацем **ниже выбранной границы**. Это не готовая рекомендация
к копированию, а материал для редакторской проверки. Список упорядочен по
релевантности запросу; сначала видны шесть фрагментов, остальные — по кнопке.
У каждого есть ссылка на конкретную статью конкурента, оба косинуса и пояснения.

Сверху вкладки — компактная агрегация по источникам: кликабельные названия статей,
число рекомендованных абзацев из каждой и полосы для их сравнения. Она обновляется
вместе с отбором и не дублирует список фрагментов ниже.

Эта вкладка содержит шкалу строгости отбора с семью положениями: «Строже»,
«Обычно», «Шире» и промежуточными делениями. Границы получаются из 10-го,
25-го, 40-го, 50-го, 60-го, 75-го и 90-го процентилей максимальных сходств
текущего расчёта. Режим «Обычно» включён по умолчанию.
Сдвиг вправо добавляет более похожие на нашу статью фрагменты; релевантность
не пересчитывается, серверный запрос не выполняется. Подпись и вопросик прямо
объясняют оба условия и влияние переключателя.

Все ссылки на статьи открываются в новой вкладке. Длинные заголовки сокращаются
только визуально на узком экране; полный заголовок остаётся в атрибуте ссылки.
Каждый косинус подписан предметно и снабжён вопросиком. Косинусы — не проценты
качества и не прогноз позиций.

### Формулировки

Только про то, что посчитали. **Запрещено**: «топ», «лидер», «зона нельзя»,
«ИИ-выборка», «пересказ топа», любые утверждения о ранжировании. Причина: конкурентов
вводят руками, это не выдача, и подкрепить такие утверждения нечем.

Вместо этого: «сходство с самым похожим фрагментом конкурентов», «материал для редакторской проверки».

## Техника

- Бекенд Node, **без Postgres, Redis, Python и LLM**.
- **Замерено 19.09:** полный прогон на четырёх страницах — 5 секунд, ответ 251 КБ (61 КБ
  в gzip), модель поднимается с диска за 0.5 секунды и занимает 144 МБ. Ставится одной
  командой `npm run model:fetch` в папку `apps/v5/api/.models` рядом с приложением.
- **SSOT на бекенде, производные в React** (как требует `AGENTS.md`). API отдаёт абзацы
  с текстом и релевантностью плюс матрицу попарных косинусов. Порогов, статусов,
  счётчиков и раскраски в ответе нет. React считает максимумы, семь границ отбора,
  средние, кандидатов и сортировку; ползунок не отправляет ни одного запроса. Объём: ~60 × ~240 чисел до трёх
  знаков ≈ 85 КБ, в gzip ~30. Векторы на клиент не отдаём.
- Состояние анализа — `Map` в памяти процесса, живёт 10–15 минут.
- `POST /analyze` → `{id}`, `GET /analyze/{id}` раз в секунду. Анализ занимает
  20–70 секунд, поэтому прогресс («загружено 4 из 6 страниц») — часть продукта.
- Лимит параллельных анализов — счётчик в памяти, не брокер. Поднять `UV_THREADPOOL_SIZE`.
- Фронт — один самодостаточный `.js`: React внутри, обычный CSS с префиксом `.sa-`
  и локальным сбросом внутри контейнера, без Tailwind preflight. Vite в режиме библиотеки.
- Встраивание: `<div id="seo-analyzer"></div>` + `<script src="...">`. Форма наша.
  Запасная дверь: `window.SeoAnalyzer.mount(el, {query, url, competitors})` — это и есть
  то, что заказчик называет «передачей параметров через jQuery». Сам jQuery не нужен.
- Локально: `npm run dev:v5`, без compose. Dockerfile добавим, когда увидим его сервер.
- Живёт в монорепе как `apps/v5`. Общих пакетов нет, при необходимости отделяется.

## Не делаем

GIST и python-сервис · краулер · LLM и рекомендации от неё · Postgres и Redis ·
общий балл 0–100 · три состояния сходства · пороги и статусы в API · квадрант · тепловую
карту матрицы · агрегацию по разделам статьи · карту векторов через PCA или MDS · ленту абзацев («ДНК статьи») ·
подтягивание настоящего топа выдачи · модальные окна.

## Порядок работ

1. Бекенд и JSON на живом примере — **сначала цифры, потом картинки**. Без реального
   распределения косинусов пороги выбирать наугад нельзя.
2. Проверить на живых данных, что дефолт ползунка даёт осмысленное разделение; согласовать фразы.
3. Виджет и сборка в один бандл.
4. Показать заказчику.

Приоритет — быстрый промежуточный результат для демонстрации, а не идеальный расчёт.
