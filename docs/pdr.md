# SEO AI Analyzer GIST — PDR

## Цель

Пользователь задаёт поисковый запрос, свой домен и домен известного конкурента.
Приложение обходит оба домена и показывает, какие материалы относятся к запросу,
где сайты повторяют друг друга и какой релевантный контент конкурента добавляет
отличающееся смысловое покрытие.

Приложение помогает исследовать контент. Оно не обещает соответствие внутренним
алгоритмам Google и не принимает редакционные решения за пользователя.

## Основной сценарий

1. Пользователь открывает список сохранённых отчётов и запускает новый анализ
   из модального окна: поисковый запрос и два домена. Введённый адрес
   приводится к origin на входной границе, поэтому ссылку на конкретную статью
   искать не нужно.
2. Приложение создаёт анализ и открывает его страницу по адресу
   `/analyses/:id`, где показывает текущий этап выполнения.
3. Краулер независимо обходит каждый домен — правила в разделе «Обход».
4. Пользователь выбирает от 1 до 30 содержательных страниц на сайт; значение по
   умолчанию — 15. Пустые, технические и непригодные страницы не расходуют этот
   лимит.
5. Из страниц извлекаются проверяемые текстовые фрагменты.
6. Семантический этап отдельно оценивает релевантность запросу и максимальную
   близость каждого фрагмента конкурента к фрагментам нашего сайта.
7. Пользователь получает сортируемый отчёт: страницы обоих доменов одной
   таблицей, тексты — по ссылке на сайте. Адрес отчёта постоянен.

## Обход

Обход детерминирован: при одном состоянии сайтов он даёт один результат.

**Область.** Введённый адрес приводится к origin, обход не выходит за него.
Ограничения по пути нет: на сайтах с плоскими адресами раздел не является
префиксом пути, и такое правило обрывало бы обход вместо того, чтобы сузить.

**Вежливость.** Читается `robots.txt`: запреты соблюдаются, между запросами к
одному домену выдерживается пауза — `Crawl-delay` сайта, если он задан.

**Где искать.** Карты сайта берутся из `robots.txt`, иначе пробуется
`/sitemap.xml`. Адрес из карты принимается по совпадению хоста: сайт нередко
объявляет карту через `http://`, отдаваясь по `https://`.

**Сравнение слов.** Запрос, текст ссылки и путь адреса режутся на слова по
не-буквенным символам; слова короче трёх букв отбрасываются, остальные
сворачиваются в общий латинский алфавит. Без этого кириллический запрос не
совпадёт с транслитерированным слагом. Два слова считаются одним, если равны
или короткое является началом длинного и само не короче четырёх букв — это
покрывает словоизменение без стеммера.

**Вес слова.** Слово запроса весит `ln(N / (1 + df))` по карте сайта, где `N` —
число адресов в ней, а `df` — сколько из них это слово содержат. Частое слово
вроде предлога весит около нуля, редкое — много. Так служебные слова гасятся без
списка стоп-слов, который пришлось бы вести вручную для каждого языка. Без карты
сайта все веса равны единице.

**Счёт.** Счёт ссылки, пути и текста — сумма весов слов запроса, для которых
нашлось совпадение. Число повторов слова не учитывается.

**Порядок.** В очередь попадают адреса из карты с ненулевым счётом и корень
домена; из очереди всегда берётся адрес с наибольшим счётом. Ссылки загруженных
страниц добавляются туда же. Query-строка сохраняется: на форумах и части CMS
весь контент живёт в параметрах. Повторы отсекаются по тексту страницы, а не по
адресу, что убирает и параметры-трекеры, и зеркала одной страницы.

**Отбор.** Обход собирает кандидатов с запасом и оставляет в отчёте страницы с
наибольшим счётом текста. Запас нужен, чтобы отчёт не рос: поднять сам лимит
страниц — значит показать втрое больше строк, а не втрое лучше выбранные. Отбор
по тексту — единственный способ найти страницу за непрозрачным адресом вида
`/news/20409`, где ни ссылка, ни путь темы не несут.

Страница содержательна, если извлечённый текст не короче порога длины. Сайт, где
таких страниц не нашлось, считается нечитаемым: так выглядит JavaScript-
приложение или закрытый раздел. Сайт вправе закрыться от обхода вовсе — ответом
об ошибке, проверкой на бота или требованием исполнять JavaScript; это его право,
и анализ в таком случае честно завершается ошибкой.

Числовые границы — бюджет посещений, запас кандидатов, размер посева из карты,
минимальные длины слова и общего начала — собраны именованными константами в
`SiteCrawlerService` и `SitemapService`. PDR фиксирует правила, значения живут в
коде в одном месте.

## Семантика оценок

- Релевантность отвечает на вопрос «насколько фрагмент относится к запросу»: это
  cosine similarity между embedding запроса и embedding фрагмента.
- Сходство отвечает на вопрос «насколько фрагмент конкурента уже похож на наше»:
  максимальный cosine по всем нашим фрагментам, со ссылкой на ближайший.
- Обе величины показываются отдельно. Один искусственный общий балл не нужен.

Порогов нет. Медианные пороги зависели только от распределения самого запуска,
поэтому доля кандидатов выходила почти постоянной при любых данных. Вместо
классификации фрагмент получает оценку `релевантность × (1 − сходство)` — она
растёт, только когда фрагмент одновременно о запросе и не похож ни на один наш.

Оценка страницы — средняя оценка нескольких её лучших фрагментов. Сумма по всем
премировала длину: статья, лишь упоминающая тему, обгоняла короткую статью о ней
за счёт числа абзацев. Среднее убирает влияние длины, а ограничение на лучшие не
даёт длинному тексту размыть себя слабыми абзацами. Сколько именно лучших — это
продуктовое решение, а не выведенное число: один означал бы «одна удачная фраза»,
все вернули бы премию за объём. Глубину страницы показывает колонка с числом
фрагментов, а не оценка.

Покрытие — средняя близость фрагментов конкурента к нашему контенту, взвешенная
по релевантности запросу.

Текст перед отправкой в модель усекается до предела её контекста; сохранённый
текст фрагмента при этом не меняется.

Отчёт называет сравниваемые домены и формулы, по которым считаются величины:
инструмент профессиональный, скрывать алгоритм незачем. Страницы обоих доменов
идут одной таблицей с колонкой домена. У наших страниц оценка и покрытие пусты —
они и есть то, с чем сравнивается конкурент, и это видно прямо в таблице. Тексты
фрагментов в отчёт не выводятся: статья открывается по ссылке. Page-to-page и
domain-to-domain cosine не вычисляются.

## Выполнение

Анализ является долгой фоновой операцией. Целевой workflow показывает этапы
`queued`, `crawling`, `crawled`, `analyzing`, `completed` и `failed`. После
`crawled` crawler worker создаёт записи страниц и ставит отдельную semantic job
для каждой страницы. После завершения всех page jobs одна финализирующая job
считает сходство фрагментов конкурента с фрагментами нашего сайта.

BullMQ и Redis отвечают за очереди, но не являются хранилищем результата. Job
выполняется одной попыткой: неудача любой job переводит анализ в `failed`.
Сетевой обход и вычисление embeddings всё равно разделены: страницы эмбеддятся
независимо друг от друга, и результат каждой сохраняется сразу.

Frontend создаёт анализ одной mutation, затем получает его состояние по `id`.
Внутренние причины сетевых и модельных ошибок не становятся контрактом UI.
Контрактом является только то, что пользователь может исправить сам: какой из
двух сайтов не удалось обойти. Причина отказа остаётся в backend logs.

## Хранение

PostgreSQL и Prisma являются единственным постоянным источником истины. Схема
состоит из анализа, связанных страниц и связанных с ними фрагментов. JSONB не
используется: текст, положение фрагмента, embedding и атомарные оценки имеют
явные поля.

Page job сохраняет embedding и релевантность каждого фрагмента своей страницы.
Финализирующая job сохраняет для фрагментов конкурента максимальное сходство и
ссылку на ближайший наш фрагмент. Итоговый отчёт собирается из тех же строк и не
дублируется отдельным JSON-документом.

Frontend вычисляет только оценку, покрытие и агрегаты текущего представления.
Лёгкий список последних анализов строится по таблице анализов.

## Границы backend

- Сетевой клиент отвечает за HTTP-запрос, timeout, статус ответа, content type и
  ограничение размера ответа. Лимит для страницы и для карты сайта разный:
  карта большого форума легко превышает лимит страницы, и общий порог отбросил
  бы её целиком.
- Экстрактор отвечает за превращение HTML в основной текст и фрагменты.
- Краулер отвечает за обход внутри origin, лимиты, порядок и отбор страниц, а
  также за вежливость к чужому серверу. Правила — в разделе «Обход».
- Семантический анализ не знает деталей HTTP и HTML.
- Граница worker переводит технические ошибки в состояние анализа.
- HTTP ExceptionFilter обрабатывает только ошибки API-запросов и не подменяет
  обработку ошибок фоновых jobs.

Timeout одного внешнего запроса является константой сетевого клиента и не
является пользовательским параметром анализа.

Ошибки группируются по границам подсистем. Не нужны отдельные классы и UI-тексты
для каждого HTTP-статуса внешнего сайта.

## Рекомендации LLM

После стабилизации числового отчёта добавляется необязательный этап
рекомендаций. Модель получает собранное представление анализа и объясняет:

- какие релевантные страницы или фрагменты конкурента стоит изучить;
- какие материалы в основном повторяют уже имеющееся покрытие;
- какие отличающиеся материалы нерелевантны запросу и потому не дают пользы.

Модель не генерирует готовые статьи и не заменяет числовой анализ.

Для интеграции адаптируется `LlmService` из локального проекта-донора
`../react-linkedin`. Один OpenAI-compatible client должен работать с удалённым
Timeweb API и локальным Ollama через конфигурацию `baseURL`, API key и названия
моделей. Отдельные реализации одного протокола не нужны.

## Вне текущего объёма

- автоматический поиск конкурентов через Google или сторонний SERP API;
- JavaScript-рендеринг внешних страниц;
- карта embeddings в 2D или 3D;
- редактирование сохранённых запусков;
- многопользовательская работа;
- генерация и публикация контента.
